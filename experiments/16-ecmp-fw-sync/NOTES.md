## ECMP 비대칭 + stateful FW

- **주입:** 두 리프의 ECMP 해시를 `출발IP+출발포트`로(Phase 1).
- **증상:** h1 → srv:80 curl 100번 중 49번 실패. 같은 서버인데 될 때와 안 될 때가 섞임(21000 성공, 21002 실패, 21003 성공 …).
- **추적:** 관측 집합으로 흐름별 경로를 맞춰 봄 → 실패 49개 = 갈 때 fw2·올 때 fw1인 흐름 49개, 정확히 일치. fw2 방명록엔 `SYN_SENT [UNREPLIED]`만 20개, fw1 drop 114.
  - 덤: 올 때(srv → h1) 해시 입력이 `srv IP + 포트 80`으로 늘 같아서 응답은 **전부** fw1로 감. 방향에 따라 해시 입력이 달라지면 이렇게 한쪽으로 쏠리기도 한다.
- **원인·복구:** 해시를 두 리프 다 5-튜플(policy 3, fields 0x37) + 같은 넥스트홉 순서 → 실패 0%.
- **교훈:** 비대칭은 방명록을 만나야 장애가 된다(Phase 0은 비대칭 54개에도 0% 실패).

## 틀린 가설: "리눅스 L4 해시(policy 1)는 대칭이다"

- **처음 가설:** 커널이 해시 전에 주소·포트를 정렬하니 policy 1이면 대칭 → 실패 0%.
- **실제:** 실패 22~23%, 1초 늦은 성공 30개 안팎, **SYN이 두 FW를 다 지난 흐름 29~32개**(같은 5-튜플인데).
- **추적:** 흐름표에서 23509 `fw1fw2 → fw1fw2`처럼 같은 흐름이 두 FW에 다 찍힘 → 재전송 때 경로가 바뀐다.
- **원인:** policy 1은 패킷에 이미 L4 해시값(`skb->hash`)이 있으면 헤더를 보지 않고 그 값을 쓴다. 로컬 소켓이 보낸 패킷엔 소켓의 무작위 txhash가 붙고, 재전송 때 새로 뽑힌다. veth는 이 값을 지우지 않고 넘긴다.
- **교훈:** "L4 해시"라는 이름만 믿으면 안 된다. 대칭이 필요하면 해시 입력을 명시(policy 3 + fields)할 것.

## conntrackd 경주

- **주입:** Phase 1의 비대칭 해시 그대로 conntrackd(FTFW, DisableExternalCache on).
- **증상:** 실패 49% → 2%. 하지만 비대칭 50개 전부 connect 1초 이상.
- **추적:** 서버 쪽 지연 1ms·10ms → connect 지연은 사라졌는데 데이터 지연(≥0.15s)은 42~49개 남음 → 처음엔 "동기화가 아직 느리다"고 봄. 지연 흐름이 전부 비대칭이고 total−connect ≈ 0.2s(RTO)라서, 두 번째 경주(SYN-ACK → h1의 ACK)라고 판단. h1 쪽에도 10ms를 주자 0.
- **원인:** 동기화(수백 µs~ms) > 랩 RTT(약 0.1ms). 상대 FW에 상태가 닿기 전에 다음 패킷이 도착한다.
- **교훈:** 동기화는 RTT보다 빨라야 이긴다. 경주는 방향마다 한 번씩, 두 번 있다.
