# 실험 19 — VXLAN의 ECMP 엔트로피: 바깥 헤더는 VTEP 쌍 하나

> [실험 목록](../../README.md) · 앞 장 [05 ECMP 분산](../../_completed/05-ecmp-hash/README.md), [16 RoCE over VXLAN](../16-roce-vxlan-ecn/README.md) · 실행 기록 [capture/run-output.txt](capture/run-output.txt)

오버레이 흐름이 아무리 많아도 VXLAN 바깥 IP 는 leaf1(10.255.1.1) → leaf3(10.255.1.3) **한 쌍**이다. 스파인을 고르는 건 leaf1 의 ECMP 해시이고, 베이스 패브릭은 `fib_multipath_hash_policy=0`(L3: 출발·목적 IP)이다.
vxlan 은 안쪽 흐름의 해시로 **바깥 UDP 출발 포트**를 바꿔 엔트로피를 싣는다. 05장은 순수 L3 흐름으로 정책을 비교했고, 이 장은 그 질문을 VXLAN 바깥 헤더로 옮긴다 — 해시가 그 출발 포트를 보는가, 큰 흐름 둘이 같은 스파인에 부딪히면 얼마나 잃는가.

## 장애 구성

```
            ┌─ eth1 (200Mbit) ── spine1 ─┐
  g1 ── leaf1                             leaf3 ── g3        VNI 10010, 바깥 10.255.1.1 → 10.255.1.3
            └─ eth2 (200Mbit) ── spine2 ─┘
          (캡처 ① eth1, ② eth2: 안쪽 흐름 출발 포트 ↔ 링크)
```

| Phase | leaf1 설정 | 보내는 것 | 보는 것 |
|---|---|---|---|
| P0 | 정책 0 (L3) | TCP 8흐름 10초 | 링크별 흐름 수, 합계 |
| P1 | 정책 1 (L4) | 같은 8흐름 | 〃 |
| P3 | 정책 3, fields 0x37 (5-튜플) | 같은 8흐름 | 〃 |
| E | 정책 1 | 큰 흐름 2개(출발 포트만 새로) × 20회 | 충돌 비율과 그때 합계 |
| Q | 정책 1 | RoCE QP 1·2·4·8 | rxe 의 QP 별 UDP 출발 포트가 갈리는가 |
| S | 정책 1 + vxlan `srcport 49152 49153` | TCP 8흐름 | 바깥 출발 포트를 하나로 묶으면 |
| C | 정책 1, 경로 캐시 비우기 유/무 | TCP 1흐름 × 12번 | (P1 결과를 보고 덧붙임) 흐름이 어느 링크로 가는가 |
| N | 정책 1 + 네 리프 vxlan `tos inherit` | TCP 8흐름, 큰 흐름 2개 × 10회 | (커널 코드를 보고 덧붙임) 경로 캐시를 끄면 갈리는가 |

## 예측 (실행 전에 적음)

- P0: 바깥 IP 쌍이 하나라 8흐름 전부 한 링크로 간다(05장의 40:0 과 같은 이유). 합계는 200Mbit 상한.
- P1: 바깥 UDP 출발 포트가 흐름마다 달라 갈린다. 합계 300Mbit 대.
- P3: P1 과 비슷하게 갈린다.
- E: 둘이 같은 링크에 갈 확률은 약 절반. 충돌이면 합 ~190, 갈리면 ~380.
- Q: rxe 는 QP 마다 출발 포트를 달리 쓰므로 QP 가 늘면 갈린다. QP 1 개는 한 링크.
- S: 출발 포트가 하나면 정책 1 이어도 P0 처럼 한 링크로 몰린다. 단, 실행 중인 vxlan 장치의 `srcport` 를 바꿀 수 있을지는 모르겠다(못 바꾸면 기록만).

## 추적 과정

1. **P1 에서 예측이 틀렸다.** 바깥 UDP 출발 포트는 흐름마다 달랐는데(캡처의 `*-flows.txt`), 정책을 0 → 1 → 3 으로 바꿔도 8흐름이 전부 spine2 였고 큰 흐름 둘은 20번 다 부딪혔다. 해시 정책을 바꿔도 링크가 한 번도 안 바뀌었다는 게 이상했다 — 해시가 아예 안 쓰이는 것처럼.
2. **캐시를 의심했다 (단계 C).** 1초짜리 흐름 하나를 12번, 매번 `ip route flush cache` 를 하고/안 하고 보냈다. 그런데 흐름 하나가 **두 링크 모두에** 찍혔다(대부분 회차가 "둘 다"). 같은 흐름의 패킷이 어떤 건 spine1, 어떤 건 spine2 로 — 흐름 해시로는 일어날 수 없는 일이다.
3. **커널 코드** (`drivers/net/vxlan/vxlan_core.c`, 6.6 `vxlan_get_route`): 출발 포트를 넣어 경로를 찾기 **전에** `dst_cache_get_ip4()` 로 캐시된 경로가 있으면 그대로 돌려준다. 이 캐시는 원격 VTEP 마다 하나이고 키에 출발 포트가 없다. 그리고 `net/core/dst_cache.c` 는 **CPU 마다 따로**(`this_cpu_ptr`) 캐시한다. 그래서 넥스트홉은 흐름이 아니라 "그 CPU 가 캐시를 채울 때 처음 찾은 경로"로 정해진다 — 오래 사는 흐름은 보통 한 CPU 에서 나가므로 한 링크로 보이고(P1), 1초짜리 흐름은 CPU 를 옮겨 다니며 두 링크에 섞였다(C).
4. 같은 함수에 `if (tos && !info) use_cache = false;` 가 있다 — **vxlan `tos` 가 0 이 아니면 캐시를 안 쓴다.** 그렇다면 `tos inherit` 로 바꾸면 흐름마다 출발 포트를 넣어 경로를 찾을 것이다 → 단계 N 에서 그대로 확인: 합계 198 → 396Mbit, 큰 흐름 충돌 20/20 → 5/10. (N 의 8흐름 중 4개가 "둘 다"로 찍힌 것은 아직 설명하지 못했다 — 흐름 시작 직후 몇 패킷이 다른 링크로 간 것으로 보이지만 확인하지 않았다.)
5. 측정 중 사고: 단계 N 을 처음 `T()` 라는 함수 이름으로 만들었다가, 공통 스크립트의 `T`(= `docker exec rtool`)와 이름이 겹쳐 함수가 자기 자신을 백그라운드로 무한히 불렀다 — 포크 폭탄으로 WSL 이 멈춰 배포판을 내렸다 올렸다. 그 회차(합계 0)는 버렸다.

## 결론

VXLAN 의 바깥 헤더는 VTEP 쌍 하나라, 오버레이 흐름이 아무리 많아도 해시가 볼 엔트로피는 바깥 UDP 출발 포트뿐이다. 05장의 교훈대로 정책 0(L3)이면 8흐름이 전부 한 스파인으로 갔고(198/400Mbit), 여기까지는 예측대로였다. 예상 밖은 정책 1·3 에서도 똑같았다는 것이다. 리눅스 vxlan 은 원격 VTEP 마다 경로를 CPU 별로 캐시하고, 캐시가 있으면 출발 포트를 해시에 넣어 보지도 않는다. 그래서 리눅스 VTEP 에서는 "리프 해시를 L4 로 바꾸면 VXLAN 도 갈린다"가 성립하지 않았다 — 큰 흐름 둘은 20번 중 20번 같은 스파인에서 부딪혀 각자 100Mbit 씩 나눠 가졌고, RoCE QP 를 8개로 늘려도 한 링크였다.
커널은 vxlan `tos` 가 0 이 아닐 때 이 캐시를 끈다. `tos inherit` 하나로 흐름마다 경로를 새로 찾게 되자 8흐름이 두 링크로 나뉘어 396Mbit, 큰 흐름 충돌은 5/10 — 이제야 해시의 확률(약 절반)대로 움직였다. 18장에서 RoCE 의 DSCP 를 살리려고 켠 바로 그 설정이 ECMP 까지 살린다는 점이 재미있다. 반대로 말하면 기본값(`tos 0`)의 리눅스 VTEP 은 QoS 표시도, 흐름별 분산도 버린다.
다음에 "링크가 두 개인데 오버레이 트래픽이 한쪽만 쓴다"를 보면, 리프 해시 정책을 고치기 전에 같은 흐름이 실제로 어느 링크로 가는지 두 업링크를 동시에 캡처해 보고, 리눅스 VTEP 이라면 `tos` 와 경로 캐시부터 의심한다. 하드웨어 VTEP 은 이 캐시가 없으니 여기 결과를 그대로 옮기면 안 된다.

## 한계

- 결론의 캐시 동작은 커널 6.6.114(WSL) vxlan 기준이다. 다른 커널 버전·`external`(collect_md) 모드·하드웨어 VTEP 은 다르게 동작할 수 있다
- 출발 포트 범위(S)는 실행 중인 장치에서 못 바꿔 재지 못했다. 장치를 새로 만들어야 하는데, FRR 의 VNI 상태까지 다시 올려야 해서 이번엔 하지 않았다
- 업링크 200Mbit 는 tc htb. 흐름 수가 적어(8, 2) 분산 비율은 확률의 한 표본이다
- N 의 "둘 다" 4흐름은 원인 미확인
