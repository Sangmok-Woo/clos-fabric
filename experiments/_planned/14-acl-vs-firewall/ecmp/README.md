# 실험 14 2부 — ECMP + 방화벽 두 대: 갈 때와 올 때 다른 경비실

> [1부 ACL vs 방화벽](../README.md) · [실험 목록](../../../README.md) · 실험 노트 [NOTES.md](NOTES.md) · 실행 기록 [capture/run-output.txt](capture/run-output.txt)

1부 Phase 5(비대칭 라우팅)를 일부러 만든 뒷문이 아니라 **ECMP가 저절로 만드는** 상황으로 옮긴다. 경로가 두 개고 길마다 FW가 하나씩 있을 때, 갈 때와 올 때를 서로 다른 리프가 따로 해시하면 같은 대화가 다른 FW로 갈린다. 그러면 "가끔만 안 되는" 장애가 된다. 그걸 재고, 두 가지 해결책 **① 대칭 해시**(같은 경비실로 보내기)와 **② 방명록 동기화 conntrackd**(어느 경비실이든 알게 하기)를 비교한다.

## 구성

```
                 ┌── fw1 ──┐
   h1 ── leafA ──┤    ║    ├── leafB ── srv
                 └── fw2 ──┘
                      ║ 동기화 전용 링크 10.15.99.0/24 (conntrackd, Phase 4)
```

| 노드 | 역할 |
|---|---|
| leafA | h1 → srv 방향 ECMP (`10.15.2.0/24 nexthop fw1 nexthop fw2`) |
| leafB | srv → h1 방향 ECMP (`10.15.1.0/24 nexthop fw1 nexthop fw2`) |
| fw1, fw2 | 1부와 같은 stateful 규칙(`nft/fw.nft`) + 관측 테이블(`nft/obs.nft`) |

베이스 패브릭과 따로 뜨는 작은 랩(`fwecmp`)이다. 이미지는 1부 `fwlab:1`에 conntrackd를 더한 `fwlab:2`. 1부와 같은 이유로 `network-mode: none`.

**측정 방법:** 회차마다 h1 → srv:80 curl 100번(출발포트만 다름, 20개씩 동시). FW 두 대의 관측 테이블이 SYN과 SYN-ACK을 볼 때마다 h1 출발포트를 집합에 적는다(ct 없이, priority -10). 그래서 흐름마다 **갈 때 FW · 올 때 FW · 성공 여부 · 걸린 시간**을 맞춰 볼 수 있다 → `capture/<회차>.tsv`.

### 해시 손잡이 (리눅스 커널)

| 설정 | 뜻 |
|---|---|
| `fib_multipath_hash_policy=0` | L3: 출발·목적 IP |
| `=1` | L4: 5-튜플 — **단, 패킷에 이미 L4 해시값이 있으면 그걸 쓴다** (Phase 2c) |
| `=3` + `fib_multipath_hash_fields` | 넣을 칸을 고른다. `0x11` = 출발IP+출발포트(방향 따라 달라짐), `0x37` = 5-튜플 |

커널은 해시에 넣기 전에 두 주소·두 포트를 크기순으로 정렬한다. 그래서 5-튜플을 다 넣으면(0x37) 왕복이 같은 값이 되고, 한쪽 칸만 넣으면(0x11) 방향에 따라 값이 달라진다.

## 결론

비대칭 자체는 장애가 아니다. 필터가 없을 때(Phase 0)는 54개 흐름이 갈 때와 올 때 다른 FW를 지났는데도 100개가 다 성공했다. 장애의 조건은 **비대칭 + 방명록**이다. FW가 방명록을 쓰는 순간(Phase 1) 비대칭 흐름 49개가 정확히 전부 실패했고 대칭 51개는 전부 성공했다. 같은 h1 → srv:80인데 출발포트에 따라 성공·실패가 섞여 나오니 사용자 눈엔 "가끔 안 되고, 새로고침하면 될 때도 있다"가 된다. 실패한 흐름의 SYN을 본 FW(fw2)엔 `SYN_SENT [UNREPLIED]`만 20개 쌓였고, SYN-ACK이 도착한 FW(fw1)는 기록에 없는 손님 114개를 버렸다.

비대칭이 생기는 길은 셋을 확인했다. 해시에 방향 따라 달라지는 칸만 넣을 때(Phase 1, 49%), 두 리프의 해시 방식이 다를 때(2a, 50%), 그리고 **해시가 완벽히 대칭이어도 넥스트홉 순서가 다를 때**(2b, 100%)다. 2b는 같은 해시값이 한쪽에선 1번, 다른 쪽에선 2번 FW를 가리키니 모든 흐름이 갈렸다. 가장 의외는 2c였다. 리눅스 기본 "L4 해시"(policy 1)는 패킷에 이미 해시값이 붙어 있으면 헤더 대신 그걸 쓰는데, 로컬 소켓이 보낸 패킷엔 소켓마다 무작위인 txhash가 붙어 있고, 이 값은 **재전송 때 새로 뽑힌다**. 그래서 같은 5-튜플인데도 SYN이 두 FW를 다 지난 흐름이 29개 나왔다. 실패율 22%에 1초 늦은 성공 28개가 섞여, Phase 1보다 증상이 더 흐릿했다. 실제 리눅스 라우터에선 NIC의 RSS 해시가 같은 자리를 차지한다.

**해결 ① 대칭 해시**(두 리프 다 5-튜플, 넥스트홉 순서 같게)는 비대칭 0, 실패 0%, 분산 42:58이다. 해시 계산 하나로 끝나서 비용이 없다. 다만 조건이 셋(대칭인 함수, 같은 함수, 같은 순서)이고 하나만 어긋나도 2a~2c가 된다. "대칭이면 된다"며 L3 해시로 가면(3b) 실패는 0이지만 h1 ↔ srv 전부가 한 FW로 몰려 ECMP를 쓰는 의미가 없어진다.

**해결 ② conntrackd**는 해시를 그대로 둔 채 실패율 49% → 2%로 떨어뜨렸다. 그런데 랩 그대로(RTT 약 0.1ms)에선 비대칭 흐름 50개가 **전부** connect에 1초가 걸렸다. 동기화 메시지가 상대 FW에 닿기 전에 SYN-ACK이 먼저 도착해 버려지고, 서버가 1초 뒤 SYN-ACK을 다시 보낼 때에야 통과한 것이다. 예상한 경주 조건이 그대로 나왔다. 경주는 두 번 있다. 첫 번째는 SYN → SYN-ACK이고 서버 쪽 지연만 늘리면 이긴다(4b: connect 지연 0). 두 번째는 SYN-ACK → h1의 ACK인데, 서버 쪽 지연은 이걸 못 도와서 데이터 지연(≥0.15s, ACK·GET 재전송) 49개가 그대로 남았다. 클라이언트 쪽에도 10ms를 주자(4d) 지연까지 0이 됐다. **동기화는 왕복 시간보다 빨라야 이긴다.** 그래서 인터넷 클라이언트처럼 RTT가 긴 경계에선 통하고, 수십 µs짜리 데이터센터 동서 트래픽에선 매 연결 1초씩 늦어진다.

**한 줄:** ECMP 뒤 stateful FW는 갈 때와 올 때를 서로 다른 장비가 해시하니 같은 대화가 다른 FW로 갈려 "가끔만" 실패한다. 데이터센터 안에선 대칭 해시(두 리프 같은 5-튜플 함수, 같은 넥스트홉 순서)가 정답이고, conntrackd는 RTT가 동기화 지연보다 긴 경계에서만 안전한 보험이다.

다음에 "가끔 안 되고 새로고침하면 된다"를 만나면 FW 두 대의 `conntrack -L`에서 `UNREPLIED`가 한쪽에만 쌓이는지부터 본다. 리눅스 라우터면 `fib_multipath_hash_policy`가 1인지(무작위 txhash·RSS 해시를 쓰는지)도 본다.
