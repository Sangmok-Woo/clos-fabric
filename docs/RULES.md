# RULES — 이름·번호·주소·포트 규칙과 결정 기록

> **이 문서의 쓸모** — 리프나 스파인을 추가할 때 **사람이 판단할 것을 0으로 만드는** 게 목표다.
> 모든 값이 "장비 번호 하나"에서 계산되어 나오면, 그때 비로소 생성기를 붙일 수 있다.
> 반대로 규칙이 없으면 생성기를 만들어도 예외 처리가 쌓여 지금과 같은 상태로 돌아온다.
>
> 규칙과 현재 랩이 어긋나는 곳은 §7에 목록으로 모아뒀다. 아직 고치지 않았다.

이 문서는 "왜 이렇게 하나"만 적는다. 따라 하는 절차는 [RUNBOOK.md](RUNBOOK.md), 무엇이 언제 바뀌었는지는 [CHANGELOG.md](../CHANGELOG.md).

## 1. 이름 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 스파인 | `spine<번호>` | spine1, spine2 |
| 리프 | `leaf<번호>` | leaf1 … leaf16 |
| 서버 | `h<리프번호>` (한 랙에 여럿이면 뒤에 a,b) | h3, h3b |
| 컨테이너 | containerlab이 `clab-<랩이름>-<노드>`로 붙인다 | clab-clos-leaf3 |

**번호는 재사용하지 않는다.** leaf4를 철거해도 다음 리프는 leaf5다. 번호를 되쓰면 옛 문서·모니터링·티켓이 다른 장비를 가리키게 된다.

스크립트는 **이 이름 규칙만 믿고** 장비 목록을 만들어야 한다. 지금처럼 `for n in leaf1 leaf2 leaf3 leaf4`라고 나열해 두면 대수가 바뀔 때마다 스크립트가 먼저 거짓말을 한다.

## 2. 번호(AS) 규칙

| 대상 | 규칙 | 범위 |
|---|---|---|
| 스파인 AS | `65000 + 번호` | 65001 ~ 65099 (99대) |
| 리프 AS | `65100 + 번호` | 65101 ~ 65199 (99대) |
| 더 커지면 | 4바이트 ASN `4200000000 + 번호` | 사실상 무제한 |

**지금 방식(`6501` 뒤에 번호를 이어 붙임)은 리프 10대에서 깨진다.** leaf10 → 650110 이 되는데 2바이트 ASN 상한은 65535다. 더하기로 바꾸면 이 문제가 사라진다.

> 스파인과 리프의 대역을 100 단위로 갈라 두는 이유: `show ip bgp` 화면에서 AS 번호만 보고 "스파인이냐 리프냐"를 즉시 구분하기 위해서다. 장애 중에는 이 1초가 크다.

## 3. 주소 규칙

전부 **장비 번호로부터 계산**된다. 주소를 "정하는" 일은 없다.

| 용도 | 계산식 | 예 (spine1 ↔ leaf3) |
|---|---|---|
| 스파인 루프백 | `10.255.0.<번호>/32` | 10.255.0.1 |
| 리프 루프백 | `10.255.1.<번호>/32` | 10.255.1.3 |
| 링크(스파인 쪽) | `10.1.<스파인번호>.<(리프번호-1)×2>/31` | 10.1.1.4/31 |
| 링크(리프 쪽) | 위 주소 +1 (항상 홀수) | 10.1.1.5/31 |
| 서버망 | `172.16.<리프번호>.0/24`, 게이트웨이 `.1`, 서버는 `.10`부터 | 172.16.3.0/24 |
| VNI | `10000 + VLAN ID` | VLAN 10 → 10010 |
| RT | `65000:<VNI>` — **패브릭 공통 고정값** | 65000:10010 |

> **링크 두 줄은 폐기 예정** — unnumbered 채택(§5-2)으로, §7 재배포 때 스위치 간 링크에서 IP가 없어진다.

**RT를 고정값으로 두는 이유**는 이미 겪었다. FRR은 RT를 `내 AS:VNI`로 자동 생성하는데, 리프마다 AS가 다르면 보내는 쪽과 기다리는 쪽이 어긋나 EVPN이 조용히 안 붙는다.

**링크 주소가 스파인당 하나의 /24 안에 모이는 게 중요하다.** spine1의 모든 링크는 `10.1.1.0/24`, spine2는 `10.1.2.0/24`. 이 덕분에 §5의 동적 이웃을 한 줄로 쓸 수 있다. (listen range가 기각되면서 이 이유도 함께 사라졌다)

### 상한

| 항목 | 한계 | 무엇이 먼저 걸리나 |
|---|---|---|
| 리프 | 99대 | AS 대역 (§2). 링크 주소 상한(`(N-1)×2+1 ≤ 255`, 128대)은 unnumbered 전환으로 없어진다 |
| 스파인 | 99대 | AS 대역 (업링크 예약 구간 10을 확정하면 10대) |
| 서버망 | 254 랙 | 3옥텟 |
| 루프백 | 254대 | 4옥텟 |

## 4. 포트 할당 규칙

**지금 구조에서 가장 위험한 부분이다.** 리프의 `eth3 = 서버`가 고정이라, 스파인을 3대로 늘리면 서버 포트가 밀리고 토폴로지·설정·스크립트가 한꺼번에 어긋난다.

### 규칙: 구간을 미리 갈라둔다

```
리프
  eth1  ~ eth10   업링크 예약 구간   (i번 포트 = spine i, 안 쓰는 번호는 비워둔다)
  eth11 ~         서버 구간          (h<리프번호> 부터 차례로)

스파인
  eth<리프번호>    = leaf<번호>       (리프 번호와 포트 번호를 일치시킨다)
```

핵심은 **"업링크 10개를 예약해 둔다"**는 것이다. 스파인이 2대에서 4대로 늘어도 서버 포트 번호는 그대로다. 실장비에서도 같은 이유로 업링크용 고속 포트 영역을 따로 잡아둔다. 예약 구간의 크기(10)는 "이 패브릭이 갈 수 있는 스파인 최대 대수"를 뜻하므로, 정하는 순간 설계 결정이 된다.

스파인 쪽에서 **포트 번호와 리프 번호를 일치**시키면 `show interface` 한 줄만 보고 어느 랙인지 알 수 있다. 리프를 철거해도 그 포트는 비워둔다(번호 재사용 금지와 같은 이유).

## 5. BGP 이웃 정책 — 정적이냐 동적이냐 (→ 동적은 기각, §5-2)

### 검증 결과 (2026-08-25, 이 랩에서 실측)

스파인의 이웃 목록을 전부 지우고 대역만 열어 두는 방식을 확인했다.

```
 bgp listen range 10.1.1.0/24 peer-group FABRIC
 bgp listen limit 128
```

- 리프 4대가 **20초 안에 스스로 다시 붙었다** (`show ip bgp summary`에서 `*leaf1` 처럼 앞에 `*`가 붙으면 자동 생성된 이웃이다)
- 서버 통신·ECMP 모두 정상 유지
- 스파인 설정에서 **이웃 8줄이 1줄로** 줄었다. 리프를 128대로 늘려도 이 줄 수는 그대로다
- 재현: `./scripts/listen-range-test.sh` (확인 후 자동 원복)

### 채택할 때 따라오는 조건

| 필요한 것 | 이유 |
|---|---|
| `neighbor FABRIC password <암호>` | 대역 안이면 누구나 붙을 수 있다. 최소한의 신원 확인 |
| `neighbor FABRIC ttl-security hops 1` | 한 홉 밖에서 온 세션을 거부한다 |
| `bgp listen limit <수>` | 세션 폭주로 스파인 메모리가 마르는 것을 막는다 |
| 기대 대수를 아는 모니터링 | **자동으로 붙으니, "붙어야 할 리프가 안 붙은 것"을 사람이 못 알아챈다** |

### 잃는 것

이웃별 `description`을 못 붙인다. 실측에서 Desc 칸이 `leaf1` → `FRRouting/10.2.1_git`으로 바뀌었다. 상대가 알려주는 hostname에 의존하게 되므로, **모든 장비의 `hostname`을 이름 규칙(§1)대로 정확히 맞춰두는 것이 전제**가 된다.

### 결론 (2026-08-25 시점)

- **스파인**: 동적(listen range) — 리프가 늘어나는 쪽이므로 효과가 크다
- **리프**: 정적 — 스파인은 자주 안 늘고, 업링크는 명시적인 편이 장애 때 읽기 쉽다

> **2026-09-10 기각** — §5-2의 unnumbered를 채택하면서 불필요해졌다. listen range는 "IP 대역"을 여는 기능인데, unnumbered에서는 링크에 IP가 없다.

## 5-2. 링크 주소 — 번호(/31)냐 unnumbered냐

### 검증 결과 (2026-09-10, 이 랩에서 실측)

spine1↔leaf1 한 링크만 바꾸고 나머지 3링크는 `/31` 그대로 둔 **혼합 상태**에서 확인했다.
양쪽에서 `/31`을 지우고, 이웃을 IP 대신 **인터페이스 이름**으로 지정한다.

```
interface eth1
 no ip address 10.1.1.0/31
router bgp 65001
 neighbor eth1 interface peer-group FABRIC     ← FABRIC에 remote-as external이 있으니 이 한 줄이면 된다
 neighbor eth1 description leaf1
```

| 확인 | 결과 |
|---|---|
| ① 세션이 fe80으로 붙나 | 10초 안에 Established. Local/Foreign host 둘 다 `fe80::…`, `Extended nexthop: advertised and received` (IPv6 링크로 IPv4 경로를 나르는 RFC 5549가 양쪽에서 협상됨) |
| ② 넥스트홉이 fe80인가 | spine1 `show ip route 172.16.11.0/24` → `fe80::a8c1:abff:fe60:5079, via eth1`. 커널에도 `via inet6 fe80::… dev eth1` |
| ③ 혼합 상태에서 통신 | leaf1 → h4 서버망 ECMP가 `fe80(spine1)` + `10.1.2.0(spine2)` 섞인 채로 정상. h1 → h4 ping 정상 |
| RA 설정이 필요했나 | **아니다.** `ipv6 nd ra-interval` 없이, `no ipv6 forwarding`도 그대로 둔 채 붙었다 (FRR 10.2.1) |

- 재현: `./scripts/unnumbered-test.sh` (확인 후 자동 원복)

### 판단 기준 — 둘 다 통과

1. **혼합 상태에서 문제 없었나** → 없었다. 링크 하나씩 점진 전환도 된다
2. **설정이 실제로 단순해졌나** → 그렇다

| 스파인 설정 (리프 N대) | 지금 (/31) | unnumbered |
|---|---|---|
| 인터페이스 IP 줄 | N | **0** |
| 이웃 줄 (description 포함) | 2N | 2N |
| 줄을 쓸 때 필요한 것 | 링크 IP 계산 (§3) | 포트 번호 = 리프 번호 (§4) |
| §3 링크 주소 규칙 | 필요 | **통째로 없어짐** |

줄 수보다 **"계산이 사라진다"**는 게 크다. 생성기 입장에서는 링크 주소 계산식 하나가 통째로 빠진다.

### 잃는 것

- **이웃 주소가 fe80(MAC에서 파생)이라 주소만 보고 상대를 알 수 없다.** 이웃 식별은 hostname(`show ip bgp summary`의 `leaf1(eth1)`)과 description에 의존한다 → 모든 장비의 `hostname`을 §1 이름 규칙대로 맞춰두는 것이 전제. 단 listen range와 달리 **description은 그대로 붙는다** (실측: Desc 칸 `leaf1`)
- **링크 IP로 하던 점검이 안 된다.** `ping 10.1.1.0` 같은 링크 단위 확인이 사라지고, `show ip bgp neighbors 10.1.1.0`은 `neighbors eth1`로 바꿔야 한다
- (미확인) traceroute 중간 홉에 무엇이 찍히는지 — 전체 전환 후 확인할 것

### 함정: IP를 먼저 지워야 한다

첫 시도에서는 이웃만 `eth1 interface`로 바꾸고 `/31`은 나중에 지웠다. 두 가지가 틀어졌다.

1. `/31`이 남아 있는 동안 FRR은 세션을 **IPv4로** 붙였다 (Local host `10.1.1.0`). 설정은 unnumbered인데 넥스트홉은 여전히 `10.1.1.1`
2. 그 상태에서 `/31`을 지우자 **세션은 Established인데 경로만 사라졌다.** spine1의 `172.16.11.0/24`에서 eth1 넥스트홉이 빠지고 다른 리프(→spine2→leaf1) 경유로 우회했다. 넥스트홉 `10.1.1.1`이 더 이상 직접 연결된 주소가 아니기 때문이다

순서는 **① `/31` 삭제 → ② 이웃 교체**. 이미 IPv4로 붙어 버린 세션은 `clear bgp eth1`로 다시 붙이면 fe80으로 넘어간다.

### 결론

- **채택.** 전체 전환은 §7 정리 재배포 때 한 번에 한다 — 재배포가 비싸니 몰아서 한 번만
- **스파인 동적 이웃(listen range)은 기각.** 쓸 곳이 사라졌고, 걱정하던 "아무나 붙는" 문제도 unnumbered에서는 그 포트에 꽂힌 장비만 붙는 것으로 해결된다 (link-local은 라우팅되지 않아 한 홉 제한이 저절로 걸린다)

## 6. 리프 1대 추가 — 고칠 곳이 몇 군데인가

절차 자체는 [RUNBOOK.md R4](RUNBOOK.md)로 옮겼다. 여기에는 규칙이 적용될수록 고칠 곳이 어떻게 줄어드는지만 남긴다.

| 시점 | 고칠 곳 | 무엇이 줄었나 |
|---|---|---|
| 지금 (규칙 적용 전) | 5군데 | — (리프 설정, 토폴로지, 스파인 설정 2개, 스크립트. 링크 IP를 계산해야 한다) |
| §7 재배포 후 | 5군데, 전부 계산 | 판단·검색이 사라진다. 링크 IP 계산도 없고 스파인에는 `neighbor ethN interface` 한 줄 |
| 점검 스크립트 수정 후 | 4군데 | 스크립트가 장비 목록을 스스로 찾는다 |
| 생성기 도입 후 | 1군데 | `fabric.yml`의 리프 수 +1 |

> 2026-08-25판에는 "§5(listen range)까지 적용하면 3군데 — 스파인 설정 2개가 빠진다"고 적었다. listen range 기각으로 그 단계는 없어졌다. unnumbered에서도 스파인은 포트마다 이웃 한 줄이 필요하다.

## 7. 현재 랩이 규칙과 어긋나는 곳

고치는 순간 랩 전체를 다시 배포해야 하므로, 아직 손대지 않았다.

| 항목 | 지금 | 규칙 | 영향 |
|---|---|---|---|
| 리프 AS | `6501`+번호 (65011…) | `65100 + 번호` | 리프 10대에서 깨진다 |
| 서버망 | `172.16.1<번호>.0/24` | `172.16.<번호>.0/24` | 리프 100대에서 자릿수가 밀린다 |
| 리프 서버 포트 | eth3(L3), eth4(EVPN) | eth11, eth12 | **스파인 증설 시 전부 밀린다** |
| 스파인 포트 | eth\<리프번호\> | 동일 | 이미 규칙 준수 |
| 링크 주소 | `/31` (`10.1.<스파인>.<…>`) | unnumbered (§5-2) | 재배포 때 삭제. 링크 IP를 쓰는 스크립트(`days.sh` 약 20곳)도 같이 |
| RT | 65000:VNI 고정 | 동일 | 이미 규칙 준수 |
| 점검 스크립트 | 세션 수 4/2, 포트 eth1/eth2, 장비명 나열이 상수 | 이름 규칙에서 유도 | 대수가 바뀌면 점검이 먼저 틀린다 |

## 8. 규약 — 확장을 계속 싸게 유지하려면

1. **고장 주입은 런타임으로만 한다** (`vtysh`, `ip link`). 설정 파일을 고쳐서 고장을 내면, 나중에 생성기를 붙였을 때 "재생성이 고장을 지우는" 충돌이 난다. 30일 코스도 이 원칙을 지킨다.
2. **점검 스크립트에 기대값을 상수로 박지 않는다.** 장비 수는 `containerlab inspect`나 인벤토리에서 가져온다.
3. **생성기를 붙인 뒤에는 생성물을 손으로 고치지 않는다.** 강제 방법: 재생성 후 `git diff --exit-code`가 깨끗한지 검사.
4. **번호는 재사용하지 않는다** (§1).
