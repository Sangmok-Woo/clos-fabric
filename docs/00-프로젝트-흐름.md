## 1. 왜 spine-leaf 인가

**옛날 데이터센터는 회사 조직도처럼 생겼다.** 맨 위에 코어 스위치, 그 밑에 배포 스위치, 맨 아래 랙 스위치.
서버가 인터넷에 나가는 트래픽(위아래로 흐르는, **North-South**)이 대부분이던 시절에는 이게 맞았다.

**지금은 서버끼리 옆으로 주고받는 트래픽(East-West)이 훨씬 많다.** 웹서버 → API → DB → 캐시,
분산 스토리지 복제, 쿠버네티스 파드끼리의 통신. 트리 구조에서는 옆 랙에 가려고 매번 꼭대기까지 올라갔다 내려와야 하고,
꼭대기 링크가 병목이 된다. 게다가 옆 랙이 "가까운 랙"이냐 "먼 랙"이냐에 따라 지연이 달라져서, 성능이 서버 배치에 좌우된다.

**Clos(=spine-leaf)는 그 문제를 "층을 두 개로 줄이고, 모든 리프를 모든 스파인에 연결"해서 푼다.**

- 서버가 붙는 스위치 = **리프(leaf)**. 랙 하나에 한 대.
- 리프끼리 연결해주는 층 = **스파인(spine)**. 스파인끼리는 **절대 연결하지 않는다.**
- 어느 랙 → 어느 랙이든 무조건 `리프 → 스파인 → 리프`, **딱 3홉.** 거리가 균일해진다(=예측 가능한 지연).
- 대역폭이 모자라면 스파인을 한 대 더 꽂는다. 모든 리프에서 그 스파인으로 한 가닥씩 늘어나므로 **가로로 증설**된다.

비유하자면 트리 구조가 "본사–지사–지점" 결재 라인이라면, Clos는 **모든 부서가 공용 복도 여러 개를 공유하는 사무실**이다.
복도(스파인)가 하나 막혀도 옆 복도로 돌아가면 되고, 붐비면 복도를 하나 더 뚫는다.

## 2. 전체 그림 (지금 배포된 상태)

```
                        AS 65001                    AS 65002
                     ┌───────────┐               ┌───────────┐
                     │  spine1   │               │  spine2   │      ※ 스파인끼리는 연결 없음
                     │10.255.0.1 │               │10.255.0.2 │
                     └┬──┬──┬──┬─┘               └┬──┬──┬──┬─┘
        10.1.1.0/31 ─┘  │  │  └─ 10.1.1.6/31      │  │  │  └─ 10.1.2.6/31
                        │  └───────────┐   ┌──────┘  │  └────────┐
        ┌───────────────┘              │   │         │           │        (리프마다 스파인 2개로 각각 1가닥)
        │        ┌─────────────────────┼───┘         │           │
   ┌────┴────┐ ┌─┴───────┐        ┌────┴────┐   ┌────┴────┐
   │  leaf1  │ │  leaf2  │        │  leaf3  │   │  leaf4  │
   │AS 65011 │ │AS 65012 │        │AS 65013 │   │AS 65014 │
   │10.255.1.1│ │10.255.1.2│      │10.255.1.3│  │10.255.1.4│
   └─┬─────┬─┘ └────┬────┘        └─┬─────┬─┘   └────┬────┘
     │eth3 │eth4    │eth3           │eth3 │eth4      │eth3
   ┌─┴──┐┌─┴──┐  ┌──┴─┐          ┌──┴─┐┌─┴──┐    ┌──┴─┐
   │ h1 ││ v1 │  │ h2 │          │ h3 ││ v3 │    │ h4 │
   └────┘└────┘  └────┘          └────┘└────┘    └────┘
  172.16.11.10   172.16.12.10   172.16.13.10    172.16.14.10   ← 랙마다 다른 서브넷 (L3, 1~3단계)
        10.10.10.11 ────── 같은 서브넷 ──────  10.10.10.33     ← 랙을 넘는 L2 (VXLAN/EVPN, 4단계)
```

읽는 법 세 가지만 잡으면 된다.

| 무엇 | 주소 | 왜 이렇게 |
|---|---|---|
| 라우터 이름표(루프백) | 스파인 `10.255.0.x` / 리프 `10.255.1.x` | 어느 링크가 끊겨도 살아 있는 주소가 필요하다. BGP router-id와 VXLAN 터널 출발지로 쓴다 |
| 스위치 간 링크 | `10.1.<스파인번호>.<...>/31` | **/31** = 주소 2개짜리 서브넷. 라우터 둘만 마주보므로 그거면 충분하고, /30 대비 주소를 절반만 쓴다 |
| 서버망 | `172.16.1<리프번호>.0/24` | **랙마다 서브넷이 다르다.** 이게 Clos의 기본형. 랙을 넘는 통신은 전부 라우팅(L3)으로 처리 |

> 이 그림은 **지금 배포된 상태**다. 확장 작업 3번(재배포) 후에는 리프 AS·서버망·서버 포트가 바뀌고, 스위치 간 링크의 `/31`은 없어진다(unnumbered). → §4의 표

**AS 번호를 장비마다 다르게 준 게 핵심이다.** 데이터센터 안인데도 iBGP가 아니라 **eBGP**를 쓴다(RFC 7938).
이유는 단순하다 — eBGP는 AS 경로만 보고 루프를 막으므로 리프를 100대로 늘려도 설정이 리프당 2줄씩만 늘어난다.
iBGP였다면 라우트 리플렉터를 따로 세워야 한다.

- 결과: BGP 세션 8개(스파인당 4, 리프당 2)가 자동으로 붙는다.

### 2단계 — 언더레이 eBGP와 ECMP

리프는 자기 루프백과 자기 서버망을 광고하고, 스파인은 그걸 다른 리프에게 전달한다. 설정에서 중요한 세 줄:

| 설정 | 뜻 | 없으면 |
|---|---|---|
| `no bgp ebgp-requires-policy` | 정책 없이도 광고 허용 | 실습에서 아무 경로도 안 나간다(실무에선 반대로 정책을 반드시 건다) |
| `maximum-paths 64` | 동일 비용 경로를 여러 개 살려둔다 | 스파인 2대 중 1대만 쓰고 나머지는 논다 |
| `bgp bestpath as-path multipath-relax` | AS 경로 **길이만** 같으면 ECMP로 인정 | 스파인 AS가 서로 달라서(65001 vs 65002) 경로가 하나로 접힌다 ← **Clos에서 제일 흔한 함정** |

검증 (`./scripts/check.sh`):

```
leaf1 → 172.16.14.0/24 : nexthop 2      ← 스파인 두 대 모두를 통해 간다
h1 → h4 traceroute     : 172.16.11.1 → 10.1.1.0 → 10.1.1.5 → 172.16.13.10   (3홉)
```

**여기서 한 번 더 파봤다 — "경로가 2개"라고 실제로 반씩 나눠 가는 건 아니다.**
리눅스의 ECMP 해시 기본값은 출발지·목적지 **IP만** 본다. h1→h4는 IP 쌍이 하나라 흐름이 아무리 많아도 한쪽 링크로 몰린다.

```
./scripts/ecmp-hash.sh      # 목적지 포트만 다른 UDP 흐름 40개를 던져서 링크별로 센다
[해시 정책 0] eth1(→spine1) +41   eth2(→spine2) +1     ← 사실상 한쪽만 쓴다
[해시 정책 1] eth1(→spine1) +12   eth2(→spine2) +30     ← 포트까지 보니 갈린다
```

→ 리프에는 `net.ipv4.fib_multipath_hash_policy=1`을 반드시 박아둬야 한다.
(그래도 12:30 으로 치우친 건 해시가 랜덤이라 그렇다. 흐름이 많아질수록 평평해진다.)

### 3단계 — 장애를 넣고 몇 초 끊기는지 재기

0.2초 간격으로 핑을 때리면서 장애를 주입하고, **잃은 패킷 개수 × 0.2초 = 끊긴 시간**으로 잰다.
ECMP라서 핑이 어느 스파인을 타는지 매번 다르므로, 스크립트가 먼저 링크 카운터로 **현재 경로를 찾아낸 뒤 그쪽을 죽인다.**

| 장애 | 방법 | 끊긴 시간 |
|---|---|---|
| 케이블이 뽑힘 | `ip link set eth1 down` | **0.2초** (1개 손실) |
| 스파인이 조용히 먹통 | 포워딩 끄고(`ip_forward=0`) 프로세스 정지(`docker pause`) | **7.6초** (38개 손실) |
| 같은 먹통 + BFD 적용 | `./scripts/bfd-apply.sh on` 후 재실행 | **0.8초** (4개 손실) |

읽는 법:

- **링크가 물리적으로 죽으면 BGP는 즉시 안다.** 인터페이스가 내려가면 세션도 같이 내려가니까. 그래서 0.2초.
- **문제는 "링크는 살아 있는데 상대가 죽은" 경우다.** 스위치 CPU가 멎거나 소프트웨어가 걸린 상황.
  BGP는 keepalive를 못 받고 **hold timer(여기선 9초)**가 다 될 때까지 기다린다. 그동안 패킷은 계속 죽은 쪽으로 간다 → 7.6초 블랙홀.
- **BFD는 이걸 위한 장치다.** 300ms마다 "살아있냐" 신호를 주고받다가 3번 놓치면 죽었다고 BGP에 통보한다 → 0.8초.
  BGP 타이머를 1초로 줄이는 것보다 가볍다(BFD는 전용 프로세스가 짧은 패킷만 주고받으므로 CPU에 부담이 적다).

### 4단계 — VXLAN / EVPN, 랙을 넘는 L2

여기까지는 "랙마다 서브넷이 다르다"가 전제였다. 그런데 실무에서는 **랙이 달라도 같은 서브넷에 있어야 하는** 요구가 나온다.
VM을 다른 랙으로 옮기는데 IP는 그대로여야 하거나, 클러스터가 브로드캐스트로 서로를 찾거나.

**VXLAN은 이더넷 프레임을 UDP 안에 넣어 실어나르는 택배 상자다.** 리프가 상자를 싸고(캡슐화) 반대편 리프가 뜯는다.
그 상자를 어디로 보낼지(어느 MAC이 어느 리프 뒤에 있는지) 알려주는 게 **EVPN**, 즉 BGP로 MAC 주소를 광고하는 것이다.

```bash
./scripts/evpn-apply.sh
```

결과:

```
leaf1 # show evpn vni
VNI    Type  VxLAN IF   # MACs  # Remote VTEPs
10010  L2    vni10010   1       1                 ← 반대편 리프를 인식

v1 → v3 (10.10.10.11 → 10.10.10.33) : 0% packet loss    ← 랙이 다른데 같은 서브넷으로 통신
leaf1 # show evpn mac vni 10010
aa:c1:ab:0c:67:9f  local   eth4
aa:c1:ab:68:f5:4a  remote  10.255.1.3                    ← 상대 MAC이 leaf3 루프백 뒤에 있다고 배웠다
```

**여기서 걸린 함정 두 개** (그대로 두면 통신이 안 된다):

1. **RT(route-target) 불일치.** FRR은 RT를 `내 AS번호:VNI`로 자동 생성한다.
   리프마다 AS가 다른 eBGP 패브릭에서는 leaf3이 `65013:10010`으로 보내고 leaf1은 `65011:10010`을 기다린다 → 서로 못 알아본다.
   → 패브릭 공통값 `65000:10010`으로 **손으로 통일**했다.
2. **스파인이 next-hop을 자기 것으로 바꿔버린다.** eBGP의 기본 동작이다.
   그러면 leaf1이 "MAC은 spine1 뒤에 있다"고 배우는데, 스파인은 VXLAN 터널 끝이 아니라서 상자를 뜯을 수 없다.
   → 스파인에 `neighbor FABRIC attribute-unchanged next-hop`.
3. (덤) 이미 붙어 있는 BGP 세션에 새 주소군(l2vpn evpn)을 켜면 `NoNeg`로 뜬다.
   기능 협상은 세션을 맺을 때 한 번만 하므로 **`clear bgp *`로 세션을 다시 맺어야** 한다.

### 5단계 — 확장 준비: 규칙부터, 그다음 검증

리프 4대로는 잘 돌지만, **한 대를 늘리려면 5군데를 사람이 손으로 고쳐야 했다.** 그래서 늘리기 전에 규칙부터 정했다
→ [RULES.md](RULES.md). 이름·AS·주소·포트가 전부 "장비 번호 하나"에서 계산되어 나오게 하는 게 목표다.

규칙을 정하면서 걸린 선택지 두 개는 랩에서 직접 돌려보고 결정했다.

| 검증 | 날짜 | 결과 | 결정 |
|---|---|---|---|
| 스파인 동적 이웃 (listen range) | 2026-08-25 | 이웃 목록을 지워도 리프 4대가 20초 안에 스스로 재접속. 스파인 이웃 8줄 → 1줄 | **기각** (unnumbered 채택으로 쓸 곳이 사라짐) |
| BGP unnumbered (한 링크) | 2026-09-10 | spine1↔leaf1만 바꾼 혼합 상태에서 넥스트홉 `fe80::… via eth1`, 섞인 ECMP·서버 통신 정상 | **채택** — 전체 전환은 확장 작업 3번 때 |

unnumbered에서 배운 함정 하나: **링크의 `/31`을 먼저 지워야 한다.** IPv4가 남아 있으면 FRR이 인터페이스 이웃을 IPv4로 붙여버리고,
그 상태에서 IP를 지우면 세션은 살아 있는데 경로만 사라진다. 자세한 건 [RULES.md §5-2](RULES.md).

순서 규칙은 두 개뿐이다. 나머지는 순서를 바꿔도 큰 탈이 없다.

- **2가 끝나기 전에 3을 시작하지 않는다.** (끝났다)
- **5는 3에 반영될 마지막 기회다.** 재배포 뒤에 바꾸면 재배포를 한 번 더 해야 한다.

### 1. unnumbered 실습 ✅

- spine1↔leaf1 한 링크만 바꾸고, 나머지 3링크는 `/31` 그대로 둔 혼합 상태에서 세 가지를 확인했다:
  ① 세션이 fe80으로 붙는다 ② 넥스트홉이 `fe80::… via eth1` ③ 서버 간 ping 정상
- RA 설정(`ipv6 nd ra-interval`)은 필요 없었다 (FRR 10.2.1)
- 설정 파일 대신 **실행 중 설정만 바꾸고 자동 원복하는 스크립트**로 남겼다 — `listen-range-test.sh`와 같은 방식
- 재현: `./scripts/unnumbered-test.sh`

### 2. 결정 + 기록 ✅

- 판단 기준 "혼합 상태에서 문제 없었나 + 설정이 실제로 단순해졌나" 둘 다 통과 → **unnumbered 채택**
- 잃는 것: 이웃 주소가 fe80이라 hostname·description으로 식별해야 한다 (description은 그대로 붙는다)
- listen range는 **기각** — 링크에 IP가 없어져 쓸 곳이 사라졌다
- 기록: [RULES.md §5-2](RULES.md), 미결정 목록에서 2건 닫음

### 3. §7 정리 재배포 (대공사)

재배포가 비싸므로 **바꿀 것을 몰아서 한 번에** 한다.

| 항목 | 지금 | 재배포 후 |
|---|---|---|
| 리프 AS | 65011 ~ 65014 | 65101 ~ 65104 |
| 서버망 | 172.16.11~14.0/24 | 172.16.1~4.0/24 |
| 리프 서버 포트 | eth3 (L3), eth4 (EVPN) | eth11, eth12 |
| 스위치 간 링크 | `/31` (10.1.x.x) | unnumbered (IP 없음) |

옛 값이 박혀 있어서 같이 고쳐야 하는 곳:

- `clos.clab.yml` — 서버 쪽 링크 포트, 서버 주소·게이트웨이
- `configs/*/frr.conf` 6개 — AS, 서버망, 링크 IP와 이웃
- `scripts/evpn-apply.sh` — 리프 AS(65011…), 서버 포트(eth4)
- `scripts/days.sh` — 링크 IP 약 20곳 + AS·서버망 (30일 코스를 계속 쓴다면)
- 문서 — RULES §3(링크 주소 규칙 삭제)·§7, 이 문서의 §2 그림

(검토) 지금 런타임으로만 넣는 **BFD(`bfd-apply.sh`)와 ECMP 해시 정책(`fib_multipath_hash_policy=1`)** 도 이번 재배포에 설정 파일로 넣을지 정하면, 재배포를 한 번 아낄 수 있다.

### 4. 점검 스크립트 수정

- 지금: 장비명 나열(`check.sh`, `bfd-apply.sh`, `evpn-apply.sh`), 기대 세션 수 4/2, 서버망 주소(`172.16.1N`, `check.sh`·`failover.sh`·`ecmp-hash.sh`)가 상수로 박혀 있다
- 바꿈: `containerlab inspect -t clos.clab.yml`의 출력(JSON 가능)에서 노드 목록을 뽑고, 이름 규칙(§1)으로 spine/leaf를 구분해 기대 세션 수를 계산한다 (스파인 = 리프 수, 리프 = 스파인 수)
- 검증: **리프 하나를 임시로 늘려도 스크립트 수정 없이 통과하는지**

### 5. 남은 결정 2개 — 3번보다 먼저

- **업링크 예약 구간 10** — "스파인이 10대를 넘을 일이 있나"만 자문하면 된다. 랩·실무 감각상 10이면 충분 → 확정만 남았다
- **4바이트 ASN** — 지금 스케일(리프 99대 상한)에서는 불필요 → "보류, 99대에 가까워지면 재검토"로 닫을 예정

### 6. 생성기

- 입력: `fabric.yml` 같은 파일에 스파인 수, 리프 수, (필요하면) VLAN 목록만
- 출력: `clos.clab.yml` + 모든 `frr.conf`. §1~4 규칙이 전부 계산식이라 코드로 옮기기만 하면 된다
- 규약 §8-3: 생성한 뒤 `git diff --exit-code`로 "손으로 고친 생성물"을 잡아낸다

### 그 다음 — 확장이 끝난 뒤

- [ ] **BFD·해시 정책을 설정 파일에 반영** — 3번 재배포에 넣지 않았다면. 지금은 `frr.conf`를 읽기 전용으로 마운트해서 `write memory`가 안 되는 구조라, 파일을 고치고 재배포하는 흐름이어야 한다.
- [ ] **모니터링** — `show`를 눈으로 보는 중. frr_exporter + Prometheus로 세션 상태/경로 수를 긁어야 한다. 기대 대수는 4번에서 만든 계산을 그대로 쓴다.
- [ ] **MTU** — VXLAN은 헤더 50바이트를 더 붙인다. 지금은 작은 핑만 해서 안 걸렸지만, 실무에서는 언더레이 MTU를 9216(점보)으로 올린다.
- [ ] **L3VNI / 멀티테넌시** — 지금 EVPN은 L2 확장(VNI 하나)까지다. VRF별 라우팅(type-5)은 미착수.

   ├─ 00-프로젝트-흐름.md          ← 지금 문서. 어디까지 왔고 다음은 무엇인가

## 6. 이 환경에서 걸렸던 것 (다음에 또 만난다)

- **WSL 배포판이 죽으면 랩도 죽는다.** 프로세스가 하나도 없으면 WSL이 배포판을 종료하고, dockerd가 재시작되면서
  컨테이너는 살아 있는데 containerlab이 만든 veth만 사라진다. 랩을 쓰는 동안은 세션을 하나 열어둘 것.
  ```bash
  powershell -c "Start-Process -WindowStyle Hidden wsl -ArgumentList '-d','Ubuntu','-u','root','--','sleep','infinity'"
  ```
- **dockerd가 저절로 안 뜬다.** WSL에 systemd가 없어서다. 랩을 띄우기 전에 `service docker start`.
- **Windows에서 `wsl ... /root/...` 를 부르면 경로가 `C:/Program...`으로 둔갑한다.** `MSYS_NO_PATHCONV=1`을 앞에 붙인다.
- **PowerShell에서 `wsl ... bash -c "..."`로 넘기면 `$`와 `\"`가 깨진다.** PowerShell이 `$(...)`를 먼저 해석하고,
  안쪽 큰따옴표 이스케이프는 bash까지 가지 못한다. 안쪽에는 작은따옴표만 쓰거나, 스크립트 파일로 만들어 실행한다.
- **메모리.** `.wslconfig`가 2GB로 묶여 있다. 라우터 6 + 서버 6 = 12대는 여유 있게 돌지만,
  리프를 16대로 늘릴 거면 `.wslconfig`부터 손봐야 한다.
