# 설계 — 기준과 이유

> 이 문서는 "무엇을 어떻게 만들었나"가 아니라 **"왜 이렇게 정했나"**를 적는다.
> 실험 방법과 실측 결과는 [EXPERIMENTS.md](EXPERIMENTS.md), 결정의 시간 순 기록은 [CHANGELOG.md](../CHANGELOG.md).

## 1. 왜 spine-leaf 인가

전통적인 3계층(코어–배포–액세스) 구조는 서버가 인터넷으로 나가는 **North-South** 트래픽 시대의 설계다.
지금의 데이터센터는 서버끼리 옆으로 주고받는 **East-West** 트래픽(마이크로서비스 호출, 스토리지 복제, 파드 간 통신)이 지배적이고, 트리 구조에서는 이 트래픽이 매번 꼭대기를 거치며 병목을 만든다. 랙의 위치에 따라 지연이 달라지는 것도 문제다.

Clos(spine-leaf)는 이를 두 가지 원칙으로 푼다:

- **모든 리프를 모든 스파인에 연결하고, 스파인끼리는 연결하지 않는다.**
  어느 랙에서 어느 랙이든 경로는 `리프 → 스파인 → 리프` 3홉으로 균일하다. 지연이 예측 가능해진다.
- **증설은 가로로 한다.** 대역폭이 모자라면 스파인을 한 대 추가한다. 기존 구조를 바꾸지 않고 모든 리프에서 한 가닥씩만 늘어난다.

## 2. 왜 eBGP 언더레이인가 (RFC 7938)

데이터센터 안인데도 iBGP가 아니라 **장비마다 AS를 하나씩 주는 eBGP**를 쓴다.

| 기준 | iBGP | eBGP (채택) |
|---|---|---|
| 루프 방지 | 풀메시 또는 라우트 리플렉터 필요 | AS 경로만 보고 자동으로 막힘 |
| 리프 100대로 늘면 | RR 계층 설계가 따라와야 한다 | 리프당 이웃 설정 2줄만 늘어난다 |
| 장애 국소화 | 도메인 전체가 하나 | AS 단위로 잘린다 |

이 선택에 따라오는 설정 세 줄이 이 랩의 뼈대다:

| 설정 | 왜 필요한가 |
|---|---|
| `maximum-paths 64` | 동일 비용 경로를 여러 개 유지한다. 없으면 스파인 2대 중 1대만 쓴다 |
| `bgp bestpath as-path multipath-relax` | 스파인마다 AS가 다르므로(65001 vs 65002), AS 경로 **길이만** 같으면 ECMP로 인정해야 한다. Clos에서 가장 흔한 함정 |
| `no bgp ebgp-requires-policy` | 실습 편의. 실무라면 반대로 경로 필터 정책을 반드시 건다 |

## 3. 주소 계획 — "정하지 않고 계산한다"

모든 주소가 **장비 번호 하나**에서 계산되어 나온다. 주소를 사람이 "정하는" 일을 없애는 것이 기준이다.

| 용도 | 계산식 | 이유 |
|---|---|---|
| 스파인 루프백 | `10.255.0.<번호>/32` | 어느 링크가 끊겨도 살아 있는 주소. BGP router-id와 VXLAN 터널 출발지로 쓴다 |
| 리프 루프백 | `10.255.1.<번호>/32` | 옥텟 하나로 스파인/리프가 구분된다 |
| 스위치 간 링크 | `/31` (스파인당 하나의 /24) | 라우터 둘만 마주보므로 주소 2개면 충분 — /30 대비 절반. **BGP unnumbered 전환이 결정되어 폐기 예정** ([EXPERIMENTS §4](EXPERIMENTS.md)) |
| 서버망 | `172.16.<리프번호>.0/24`, GW `.1` | 랙마다 다른 서브넷 — Clos의 기본형. 랙을 넘는 통신은 전부 L3 |
| VNI | `10000 + VLAN ID` | VLAN 번호만 알면 VNI가 나온다 |
| EVPN RT | `65000:<VNI>` 패브릭 공통 고정값 | FRR의 자동 생성값은 `내 AS:VNI`인데, 장비마다 AS가 다른 eBGP 패브릭에서는 서로 어긋나 EVPN이 조용히 실패한다. 실측으로 확인한 함정 |

## 4. 이름·AS·포트 규칙 — 판단을 0으로

리프 1대를 추가할 때 사람이 판단할 것이 없어야, 생성기(토폴로지·설정 자동 생성)를 붙일 수 있다.

| 대상 | 규칙 | 근거 |
|---|---|---|
| 이름 | `spine<번호>` / `leaf<번호>` / `h<리프번호>` | 스크립트가 이름 규칙만 믿고 장비 목록을 만들 수 있게 |
| 번호 | **재사용 금지** — leaf4를 철거해도 다음은 leaf5 | 번호를 되쓰면 옛 문서·모니터링·티켓이 다른 장비를 가리킨다 |
| AS | 스파인 `65000+번호`, 리프 `65100+번호` | 문자열 이어붙이기(6501+번호)는 리프 10대에서 2바이트 ASN 상한(65535)을 넘는다. 대역을 100 단위로 가르면 `show ip bgp`에서 AS만 보고 계층이 읽힌다 |
| 리프 포트 | `eth1~10` 업링크 예약, `eth11~` 서버 | 스파인이 2대에서 4대로 늘어도 서버 포트가 밀리지 않는다. 예약 구간의 크기가 곧 "스파인 최대 대수"라는 설계 결정이 된다 |
| 스파인 포트 | `eth<리프번호> = leaf<번호>` | `show interface` 한 줄로 어느 랙인지 읽힌다 |

이 규칙 아래에서 리프 1대 추가는 5군데 수정(전부 계산) → 점검 스크립트 자동화 후 4군데 → 생성기 도입 후 **1군데**(`fabric.yml`의 리프 수 +1)로 줄어든다.

## 5. 운영 원칙

1. **고장 주입은 런타임으로만 한다** (`vtysh`, `ip link`). 설정 파일을 고쳐 고장을 내면, 생성기가 재생성할 때 고장이 지워지는 충돌이 생긴다.
2. **점검 스크립트에 기대값을 상수로 박지 않는다.** 장비 수와 기대 세션 수는 토폴로지에서 계산한다. 상수로 박으면 대수가 바뀔 때 점검이 먼저 거짓말을 한다.
3. **설정은 파일로, 읽기 전용 마운트로.** 설정이 깃에 남고, 랩을 부수고 다시 세워도 같은 상태로 돌아온다.
4. **생성기를 붙인 뒤에는 생성물을 손으로 고치지 않는다.** 재생성 후 `git diff --exit-code`로 강제한다.
