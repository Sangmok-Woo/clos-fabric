# 확장 규칙 — 이름·번호·포트를 어떻게 정할 것인가

> **이 문서의 쓸모** — 리프나 스파인을 추가할 때 **사람이 판단할 것을 0으로 만드는** 게 목표다.
> 모든 값이 "장비 번호 하나"에서 계산되어 나오면, 그때 비로소 생성기를 붙일 수 있다.
> 반대로 규칙이 없으면 생성기를 만들어도 예외 처리가 쌓여 지금과 같은 상태로 돌아온다.
>
> 규칙과 현재 랩이 어긋나는 곳은 §7에 목록으로 모아뒀다. 아직 고치지 않았다.

---

## 1. 이름 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 스파인 | `spine<번호>` | spine1, spine2 |
| 리프 | `leaf<번호>` | leaf1 … leaf16 |
| 서버 | `h<리프번호>` (한 랙에 여럿이면 뒤에 a,b) | h3, h3b |
| 컨테이너 | containerlab이 `clab-<랩이름>-<노드>`로 붙인다 | clab-clos-leaf3 |

**번호는 재사용하지 않는다.** leaf4를 철거해도 다음 리프는 leaf5다. 번호를 되쓰면 옛 문서·모니터링·티켓이 다른 장비를 가리키게 된다.

스크립트는 **이 이름 규칙만 믿고** 장비 목록을 만들어야 한다. 지금처럼 `for n in leaf1 leaf2 leaf3 leaf4`라고 나열해 두면 대수가 바뀔 때마다 스크립트가 먼저 거짓말을 한다.

---

## 2. 번호(AS) 규칙

| 대상 | 규칙 | 범위 |
|---|---|---|
| 스파인 AS | `65000 + 번호` | 65001 ~ 65099 (99대) |
| 리프 AS | `65100 + 번호` | 65101 ~ 65199 (99대) |
| 더 커지면 | 4바이트 ASN `4200000000 + 번호` | 사실상 무제한 |

**지금 방식(`6501` 뒤에 번호를 이어 붙임)은 리프 10대에서 깨진다.** leaf10 → 650110 이 되는데 2바이트 ASN 상한은 65535다. 더하기로 바꾸면 이 문제가 사라진다.

> 스파인과 리프의 대역을 100 단위로 갈라 두는 이유: `show ip bgp` 화면에서 AS 번호만 보고 "스파인이냐 리프냐"를 즉시 구분하기 위해서다. 장애 중에는 이 1초가 크다.

---

## 3. 주소 규칙

전부 **장비 번호로부터 계산**된다. 주소를 "정하는" 일은 없다.

| 용도 | 계산식 | 예 (spine1 ↔ leaf3) |
|---|---|---|
| 스파인 루프백 | `10.255.0.<번호>/32` | 10.255.0.1 |
| 리프 루프백 | `10.255.1.<번호>/32` | 10.255.1.3 |
| 링크(스파인 쪽) | `10.1.<스파인번호>.<(리프번호-1)×2>/31` | 10.1.1.4/31 |
| 링크(리프 쪽) | 위 주소 +1 (항상 홀수) | 10.1.1.5/31 |
| 서버망 | `172.16.<리프번호>.0/24`, 게이트웨이 `.1`, 서버는 `.10`부터 | 172.16.3.0/24 |
| VNI | `10000 + VLAN ID` | VLAN 10 → 10010 |
| RT | `65000:<VNI>` — **패브릭 공통 고정값** | 65000:10010 |

**RT를 고정값으로 두는 이유**는 이미 겪었다. FRR은 RT를 `내 AS:VNI`로 자동 생성하는데, 리프마다 AS가 다르면 보내는 쪽과 기다리는 쪽이 어긋나 EVPN이 조용히 안 붙는다.

**링크 주소가 스파인당 하나의 /24 안에 모이는 게 중요하다.** spine1의 모든 링크는 `10.1.1.0/24`, spine2는 `10.1.2.0/24`. 이 덕분에 §5의 동적 이웃을 한 줄로 쓸 수 있다.

### 상한

| 항목 | 한계 | 무엇이 먼저 걸리나 |
|---|---|---|
| 리프 | 128대 | 링크 주소 `(N-1)×2+1 ≤ 255` |
| 스파인 | 99대 | AS 대역 |
| 서버망 | 254 랙 | 3옥텟 |
| 루프백 | 254대 | 4옥텟 |

## 4. 포트 할당 규칙

**지금 구조에서 가장 위험한 부분이다.** 리프의 `eth3 = 서버`가 고정이라, 스파인을 3대로 늘리면 서버 포트가 밀리고 토폴로지·설정·스크립트가 한꺼번에 어긋난다.

### 규칙: 구간을 미리 갈라둔다

```
리프
  eth1  ~ eth10   업링크 예약 구간   (i번 포트 = spine i, 안 쓰는 번호는 비워둔다)
  eth11 ~         서버 구간          (h<리프번호> 부터 차례로)

스파인
  eth<리프번호>    = leaf<번호>       (리프 번호와 포트 번호를 일치시킨다)
```

핵심은 **"업링크 10개를 예약해 둔다"**는 것이다. 스파인이 2대에서 4대로 늘어도 서버 포트 번호는 그대로다. 실장비에서도 같은 이유로 업링크용 고속 포트 영역을 따로 잡아둔다. 예약 구간의 크기(10)는 "이 패브릭이 갈 수 있는 스파인 최대 대수"를 뜻하므로, 정하는 순간 설계 결정이 된다.

스파인 쪽에서 **포트 번호와 리프 번호를 일치**시키면 `show interface` 한 줄만 보고 어느 랙인지 알 수 있다. 리프를 철거해도 그 포트는 비워둔다(번호 재사용 금지와 같은 이유).

## 5. BGP 이웃 정책 — 정적이냐 동적이냐

### 검증 결과 (2026-08-25, 이 랩에서 실측)

스파인의 이웃 목록을 전부 지우고 대역만 열어 두는 방식을 확인했다.

```
 bgp listen range 10.1.1.0/24 peer-group FABRIC
 bgp listen limit 128
```

- 리프 4대가 **20초 안에 스스로 다시 붙었다** (`show ip bgp summary`에서 `*leaf1` 처럼 앞에 `*`가 붙으면 자동 생성된 이웃이다)
- 서버 통신·ECMP 모두 정상 유지
- 스파인 설정에서 **이웃 8줄이 1줄로** 줄었다. 리프를 128대로 늘려도 이 줄 수는 그대로다
- 재현: `./scripts/listen-range-test.sh` (확인 후 자동 원복)

### 채택할 때 따라오는 조건

| 필요한 것 | 이유 |
|---|---|
| `neighbor FABRIC password <암호>` | 대역 안이면 누구나 붙을 수 있다. 최소한의 신원 확인 |
| `neighbor FABRIC ttl-security hops 1` | 한 홉 밖에서 온 세션을 거부한다 |
| `bgp listen limit <수>` | 세션 폭주로 스파인 메모리가 마르는 것을 막는다 |
| 기대 대수를 아는 모니터링 | **자동으로 붙으니, "붙어야 할 리프가 안 붙은 것"을 사람이 못 알아챈다** |

### 잃는 것

이웃별 `description`을 못 붙인다. 실측에서 Desc 칸이 `leaf1` → `FRRouting/10.2.1_git`으로 바뀌었다. 상대가 알려주는 hostname에 의존하게 되므로, **모든 장비의 `hostname`을 이름 규칙(§1)대로 정확히 맞춰두는 것이 전제**가 된다.

### 결론

- **스파인**: 동적(listen range) — 리프가 늘어나는 쪽이므로 효과가 크다
- **리프**: 정적 — 스파인은 자주 안 늘고, 업링크는 명시적인 편이 장애 때 읽기 쉽다
- 채택 여부는 §8의 미결정 사항. 지금 랩은 정적을 유지한다

## 6. 리프 1대 추가 절차

**지금 (규칙 적용 전) — 5군데**

1. `configs/leafN/frr.conf` 새로 작성
2. `clos.clab.yml`에 노드 + 링크 2줄
3. `configs/spine1/frr.conf`에 인터페이스 + 이웃 4줄
4. `configs/spine2/frr.conf`에 같은 것
5. 스크립트의 장비 목록·기대 세션 수 수정

**§1~4 적용 후 — 여전히 5군데지만 전부 계산으로 나온다** (판단·검색 불필요)

**§5까지 적용 후 — 3군데** (스파인 설정 2개가 빠진다)

**생성기 도입 후 — 1군데** (`fabric.yml`의 리프 수를 +1)

## 7. 현재 랩이 규칙과 어긋나는 곳

고치는 순간 랩 전체를 다시 배포해야 하므로, 아직 손대지 않았다.

| 항목 | 지금 | 규칙 | 영향 |
|---|---|---|---|
| 리프 AS | `6501`+번호 (65011…) | `65100 + 번호` | 리프 10대에서 깨진다 |
| 서버망 | `172.16.1<번호>.0/24` | `172.16.<번호>.0/24` | 리프 100대에서 자릿수가 밀린다 |
| 리프 서버 포트 | eth3(L3), eth4(EVPN) | eth11, eth12 | **스파인 증설 시 전부 밀린다** |
| 스파인 포트 | eth\<리프번호\> | 동일 | 이미 규칙 준수 |
| 링크 주소 | 규칙과 동일 | — | 이미 규칙 준수 |
| RT | 65000:VNI 고정 | 동일 | 이미 규칙 준수 |
| 점검 스크립트 | 세션 수 4/2, 포트 eth1/eth2, 장비명 나열이 상수 | 이름 규칙에서 유도 | 대수가 바뀌면 점검이 먼저 틀린다 |

## 8. 규약 — 확장을 계속 싸게 유지하려면

1. **고장 주입은 런타임으로만 한다** (`vtysh`, `ip link`). 설정 파일을 고쳐서 고장을 내면, 나중에 생성기를 붙였을 때 "재생성이 고장을 지우는" 충돌이 난다. 30일 코스도 이 원칙을 지킨다.
2. **점검 스크립트에 기대값을 상수로 박지 않는다.** 장비 수는 `containerlab inspect`나 인벤토리에서 가져온다.
3. **생성기를 붙인 뒤에는 생성물을 손으로 고치지 않는다.** 강제 방법: 재생성 후 `git diff --exit-code`가 깨끗한지 검사.
4. **번호는 재사용하지 않는다** (§1).
